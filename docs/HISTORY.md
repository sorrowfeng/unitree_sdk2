## 2026-10-29 双臂「缓起步」+ 灵巧手改双总线

### 双臂首次接管「猛甩」
- **现象**：流程启动、收到第一个 JSON 后，双臂从"放下"姿态**猛地抬起**到遥操姿态。
- **根因**：首个可执行包到达时目标瞬间变成遥操 IK 解，而限速是 `arm_vel_limit = 30 rad/s`
  ⇒ 1.5 rad（86°）只要 **50 ms**。`arm_cmd_lag_max`（20°）只限制"指令领先实测"，
  **不限制整体速度**，所以挡不住。
- **修法**：加「缓起步」——首个可执行包时 `arm.requestEngagement()`，控制器用
  `engage_vel_limit`（默认 1.0 rad/s ≈ 57°/s）慢慢追，追上后恢复 30 rad/s。1.5 rad 约 1.45 s。
- **⚠️ 踩过的坑**：不能在 `start()` 里按 `cmd_reset_` 自动进缓起步 —— 那时目标还等于"当前姿态"，
  第一个 tick 就满足"已追上"，缓起步形同虚设。改为主循环**显式请求**，并加
  `engage_min_s`（0.6 s）下限兜住"请求与首个真实目标之间还隔几个 tick"。

### 灵巧手改成「两条总线、各一只手、node 都是 1」
- 拓扑从"一条总线挂 node 1/2"改成"两条独立适配器，各挂一只手，node 都是 1"。
  两条总线的 CAN ID 完全相同（都 `0x501`/`0x481`），只能靠**适配器**区分左右。
- `LHandCanfd` 从"单总线多节点"重构成"**多总线、按 side 路由**"，回环/反馈按 side 分别统计。
- **⚠️ 新坑**：`argparse` 默认允许**长选项前缀缩写** ⇒ 旧命令 `--left 1` 被静默当成
  `--left-bus 1`、`--right 2` 当成 `--right-bus 2`，报的是"device_index=2 无效"而不是
  "参数不对"。**已全局 `allow_abbrev=False`**。
- 实测确认：`device_index 0 = 左手`、`1 = 右手`（见 `scripts/r1_hand/README.md`）。

### 工程整理
- 灵巧手整套入库 `example/r1/high_level/scripts/r1_hand/`（含 vendor 的 `canfd_lib.py`、
  `gsusb_canfd/`、pyusb 1.2.1），随 `deploy_backpack.sh` 一并同步；背包 `~/r1_hand` 改软链接。
- 新增最简启动文档 `R1_TELEOP_QUICKSTART.md`（Runbook 涨到 270 行后，"照着敲一遍"被淹没了）。

## 2026-10-09 灵巧手：绕开厂商 SDK，直发 CANFD

**硬件**：LHandPro `DH116S-L000-A1`(左) / `DH116S-R000-A1`(右)，6 自由度，USB-CANFD `a8fa:8598`。

- **SDK 为什么用不了**：`libLHandProLib.so` 在 Ubuntu 22.04/GCC 11 上编，
  要求 `GLIBCXX_3.4.30` + **`GLIBC_2.34`**；背包是 Ubuntu 20.04 / glibc 2.31
  ⇒ `ctypes.CDLL` 直接失败。**换 libstdc++ 也救不了**（glibc 是整个 C 运行时）。
- **结论**：手的 CAN 帧协议极简单，**直接发原始帧**，完全绕开 SDK。
- **⚠️ 两个骗过我的假象**：
  1. **回环 ≠ 反馈** —— 适配器把自己发出去的帧回显回来（ID 就是 `0x500+node`），
     第一版把它统计成"设备应答"，看着像 12 条回复，其实全是 TX 回显。
  2. **`00 02 50 01` 不是运动的前置条件** —— 我一度以为必须先发它，过度约束了；
     它只是"开启异步反馈上报"（发了之后约 1000 帧/秒）。
- **架构决定**：C++ 侧要用 gs_usb 就得在背包上编译 C++ 库；而 Python 那套已真机验证
  ⇒ 拆成桥：`C++ ──UDP 9998──> hand_bridge.py ──CANFD──> 手`。
- **两个长跑必踩**：逐帧日志刷屏、**stdout 块缓冲**（非 TTY 看不到进度，误判成"没跑起来"）。

## 2026-09-29 审「实机能跑了吗」：App 契约 + 两个偏离官方的地方

- **`controllers.pose` 是绝对位姿，`teleop.pose` 是校准后增量** —— 我们的公式吃绝对位姿
  ⇒ `--pico-source` 只能用 `controllers`。⚠️ `pico_sim_sender.py` 把两者填成同一份数据，
  **这个差别在仿真里永远暴露不出来**。
- **首包不再切 FSM**：原先首个可执行包自动 `StandUp()`（811→4）是**偏离官方**的一步 ——
  官方 `xr_teleoperate` 从不切 FSM（要求事先在运控态）。现只解锁底盘速度闸门，
  旧行为降级为 `--auto-stand`（**默认关**）⇒ **起程序前机器人必须已在 811**。
- **`operator_mode` 缺失可诊断**：区分「App 没发这个键」（= 装错 App）与「操作者真发了
  stop_signal」—— 两者现象一模一样（每包 `Damp()`、腿一直软），以前无法区分。
- **App 身份是最容易出事故的一条**：实机主 App 是 `:openxr-app`（`sdk="pico-openxr-single"`）；
  旧 `:app`（`sdk="pico-openxr-bridge"`）**不发 `operator_mode`** ⇒ 被兜底成 stop_signal。

## 2026-09-24 无线网卡选型（结论保留，供将来参考）

- 背包**零无线硬件**；本机已装 **AIC8800 驱动且支持 AP 模式**（第一推荐）。
- ⚠️ `mt7601u` / `rtl8xxxu` **主线没有 AP 模式** —— "能当客户端" ≠ "能开热点"，两套选型别混。
- **买卡三条件**：① 必须 **USB 口**版；② AIC8800 必须 **`DC` 变体**（固件只装了
  `/lib/firmware/aic8800DC/`，驱动里目录名写死）；③ 优先**可拆 SMA 外置天线**
  （金属背包壳 + nano 内置天线是常见翻车点）。
- **到手唯一决定性验收**：`iw list | sed -n '/Supported interface modes/,/^$/p' | grep -c AP` ≥ 1。
- ⛔ 廉价「免驱 nano 卡」大量是 `148f:7601`(MT7601U) / `0bda:8179|8178`(RTL8xxxEU)，**都无 AP**。

## 2026-09-23 首次上背包：三个硬事实 + 一个致命 bug

### 1. 背包没有无线硬件
`lsusb` 只有 2 个 root hub，无 wlan 接口。NM 里那条 `Unitree` 是 `mode=infrastructure`
的**客户端**配置，**不是**背包能广播的热点。

### 2. Ctrl+C 之谜 = fishros 的 ROS 菜单写进了 `.bashrc`
交互 shell 会弹 `ros:foxy(1) noetic(2) ?`，选 1 就导出 `CYCLONEDDS_URI` 指向写死 `eth0`
的 xml，而本机是 **`eth10`** ⇒ **DDS 静默超时**（现象跟"脚本坏了/网线断了"一模一样）。
⚠️ **tmux 里同样会弹**（tmux 起登录 shell → `.profile` → `.bashrc`，那段没有 `$TMUX` 守卫）。
⇒ **见到就按回车，永不按 1**；排查先 `echo $CYCLONEDDS_URI`。

### 3. ⚡ 速度限幅死锁（本项目最值钱的一条教训）
原实现把限速写成「**实测 + 每帧一小步**」。当偏差力矩 < 关节静摩擦时，
**指令永远追不上去，电机纹丝不动** —— 真机实测 `--vel 2` 完全不动、`--vel 30` 能动，
一度以为是硬件问题。

正确做法：限速必须作用在**指令自身**的积分上（`cmd += clamp(目标-cmd, ±vel*dt)`），
让"指令领先实测"的量**持续累积**直到克服死区；再用 `arm_cmd_lag_max`（≈20°）兜底，
防止电机被物理卡住时指令跑到远处、卡滞解除瞬间暴冲。

⇒ 两处同源，**别只改一处**：`r1_arm_manual.cpp::publishOnce()` 与
`r1_arm_controller.h::clipTargets()`。
诊断法：看「指令领先实测」是否**贴住 20° 上限** —— 贴住就是电机没跟上。

### 其它
- **构建 ≠ 影响**：编译只读写自己目录、不发 DDS；**运行才改机器人状态**。
- **tmux 的真实意义是 `SIGHUP`**：SSH 掉线/关窗口时内核给前台进程组发 `SIGHUP`，
  默认动作是**立即杀进程** ⇒ 持有 `rt/arm_sdk` 权重的程序会**冻结在最后一帧姿态**。
  现在 `SIGINT`/`SIGTERM`/`SIGHUP` 走同一条清理路径。⛔ `kill -9` 依然救不回。
